# SplitCast architecture convergence · 2026-11-20

**Design freeze for GPT-6.2 Sol Max.** Bind remote acquisition to the production generation that capture observed. Schedule production media supervision independently of Studio commands. Replace the private production microphone server with one anonymous PCM pipe if the packaged OBS passes the adoption tests. The expected effects are rejection of released Prepare requests, continued recording through a healthy slow edit, and one fewer production process per media session. The capture codec, network transport and game can support all three designs as they stand.

## 2. Execution and ownership model

**Verified in source.** One Agent per role owns the session and its child process groups. The capture host sends compressed media and keeps local playback. Production decodes, mixes, composites and encodes the final output.

## 3. Candidate assessment

The first two candidates have independent counterexamples at authenticated command entry points. The third can eliminate a process from every media session without changing the capture host. Transport and GPU changes could have larger physical effects, but the available measurements cannot attribute gameplay or production render tails to those boundaries. ## 4. Three architectural decisions

### 1. Fence acquisition at production

**Invariant.** For a completed capture-owned Stop, any in-transit acquisition from that released session must be incapable of creating another production effect. An intentionally fresh Prepare is still possible. Two capture clients observing the same idle production instance must retain distinct identities.

**Verified counterexample.** `completed_stop_is_not_a_cross_host_prepare_replay_fence` performs Prepare(A), Stop(A), checks release, then sends the same Prepare(A). It observes Ready with children again. `late_owned_start_cannot_recreate_a_completed_remote_session` rejects the analogous Start. Both tests ran on the base. The production listener stamps work when it *arrives*. The capture-generated owner says nothing about the production state when the operator authorized the request. A delayed copy arriving after Stop therefore takes the new local generation. The shipping capture Agent sends one Prepare per authorization. This reproduction requires a repeated application request and demonstrates reacquisition of preparation resources. Its frequency in the field is unknown. [Two-Agent counterexamples](https://github.com/tenzyu/splitcast/blob/ca213f8cc9b5009b603528042fea0a6eb2b271b0/packages/splitcast-rs/tests/two_agents.rs#L702-L742) · [Positive-write obligation and Stop admission](https://github.com/tenzyu/splitcast/blob/ca213f8cc9b5009b603528042fea0a6eb2b271b0/packages/splitcast-rs/src/lifecycle.rs#L226-L326)

| Choice | Reliability, cost and compatibility |
| --- | --- |
| Keep the beginning-owner reservation and add an acquisition precondition | Check the observed production revision in `begin` when it reserves an Idle peer Prepare. Keep the later phase transition and the special release proof for Stop between the two. This smaller patch can fence replay with the same paired wire change, at the cost of two places that represent a beginning owner. Remembering only the most recently released nonce instead loses protection after another owner or restart. |
| **Condition the existing owner-bearing Prepare on the observed production Idle revision** | Uses the existing random instance, generation, compatibility read and holder nonce. Constant memory, no new round trip, timer, process or persisted state. Requires matching peer versions. |
| Model acquisition as an HTTP resource with strong ETag/If-Match and conditional PUT/DELETE | Standard conditional semantics fit. Migrating the finite JSON command API, status-code clients and all views adds surface. A durable service or database would additionally need crash consistency for real OS/OBS effects. The existing command can carry the same precondition. [HTTP Semantics, section 13.1.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1) |

**Frozen change.** Bump the internal paired `transport.version` from 2 to 3 for both media and media-free contracts. In authenticated production `routes` return a sibling `prepare_id` containing the existing opaque `start_id` for Idle, read under the metadata lock with no pending Stop or expiry. Return null otherwise. Keep the comparable geometry/codec/speech contract in `transport`. Only a fresh acquisition requires a non-null ID. On tunnel restoration for cleanup, validate compatibility and use the already-held owner regardless of the returned `prepare_id`. If pending Stop or a lost connection prevents reconciliation within budget, retain the obligation.

After full compatibility succeeds, capture constructs the existing `_owner` string as `<prepare_id>-<32 lowercase hex random digits>`. For an Idle acquisition, split only at the last hyphen, validate the fixed suffix and compare the entire prefix byte-for-byte to production's current Idle ID. The maximum fits the existing 128-byte owner bound. Keep sending the complete opaque owner for Start, heartbeat, Stop and all owned calls. The suffix distinguishes two callers who saw the same revision. Authorization continues to require the production bearer.

| Event at production | Commit point and result |
| --- | --- |
| Owned Prepare from Idle | Validate pure role/purpose/argument constraints. At the point where the effect owner currently begins the dequeued request, check admitted generation, expiry, Stop, Idle revision and caller nonce under the metadata lock. Commit the real `Preparing(Peer { owner, expires })` in that same critical section, before resetting the scene or starting a worker. Every subsequent failure follows the owned compensation path. A stale or missing precondition yields `not_executed` and zero effects. |
| Duplicate for the same held owner and purpose | Preserve the existing Ready/Running success. A different holder/purpose is rejected before effects. Stop, expiry or failure forbids reactivation. Freshly authorized acquisitions use a fresh nonce. |
| Stop races dequeue | Local emergency Stop revokes previously queued work. An owner-bearing Stop before any matching acquisition has committed retains the existing conflict/unknown semantics. Once acquisition commits, matching Stop sees the phase owner and fences further dispatch. Delete the transient `active_owner` reservation and its Idle-proof special case when the committed phase covers this interval. Peer Start from Idle cannot reserve or acquire. |
| Stop completes, then old packet arrives | The completed Stop has advanced the generation. An old prefix fails even after intervening sessions. Every route returning to Idle in a surviving Agent must have invalidated the earlier Idle ID. Shutdown discards the instance. Do not bump the cancellation generation inside the acquiring request and thereby cancel its own work. |
| Write, reply or restart is lost | Retain the first-positive-write capture obligation, including a partial HTTP prefix. For an immediate 200 require a valid production `stop_id` for the held instance, the full held owner, `stop=completed`, `outcome=completed` and Idle. For a 202 save the valid admitted ID and require that exact ID on every subsequent status and the same owner-bound completion. Initial 202 carries the ID but need not echo the owner. Missing/changed tickets, bare Idle, a new instance or a different owner leave release unknown. Apply this in `cleanup_owned`, which currently compares only owner/Idle/completed. An expired matching holder retains explicit release authority. |

**Adversarial limits.** A new server incarnation rejects an old acquisition token. It cannot certify what the dead process released. If only a partial prefix arrived, or a competing caller won the acquisition, capture may lack a matching release receipt despite having written bytes. Losing the first Stop reply leaves capture without an admitted ticket. A fresh explicit owner-scoped Stop can obtain the retained immediate completion or admit a new attempt for still-held effects. Keep the original attempt unknown. A bearer holder can still explicitly prepare or emergency-stop locally. A version-2 peer or an untagged owner-bearing Prepare must fail before production allocation. D03/D13 rejected tunnel-as-authority, success-only bookkeeping and blind retries. The later instance-bound Start IDs and Stop tickets now supply the missing precondition and correlation without a durable journal. ### 2. Make media supervision independent of command latency

**Invariant.** A Running production session needs recent evidence of expected ingress and output progress. A successful control operation within its own budget must not fabricate an ingress failure. A genuine loss of observation or progress must still revoke continued operation.

**Observed on the base.** Both fixture arms used actual Agent binaries and a private recording command. The stand-ins return a larger byte count at every query. The fake OBS released its state lock after applying a scene transform, then held only that connection's reply. At 100 ms the edit returned HTTP 200 with `operation.state=applied` and production stayed Running. At 3,500 ms it returned the same success, then status reported Failed, `incoming media or OBS output stopped progressing`, no output and no children. The hold fits Studio's 5 s budget. This establishes a false failure at the real control entry point with simulated media. [Counter generation and per-connection hold](https://github.com/tenzyu/splitcast/blob/ca213f8cc9b5009b603528042fea0a6eb2b271b0/packages/splitcast-rs/tests/two_agents.rs#L1133-L1158)

**Mechanism.** `serve_agent` calls `tick` and then executes one ordinary command to completion on the same thread. Production's one-second health check calls `ReceiveMonitor::observe`, which requires increasing bytes *and* at most three seconds since its own previous sample. A valid blocked edit consumes that interval. The next sample fails even if every byte counter grew. `Agent::fail` then compensates and stops output. Increasing a queue limit cannot run a sample during the edit. [Effect owner](https://github.com/tenzyu/splitcast/blob/ca213f8cc9b5009b603528042fea0a6eb2b271b0/packages/splitcast-rs/src/agent.rs#L1115-L1146) · [Health decision](https://github.com/tenzyu/splitcast/blob/ca213f8cc9b5009b603528042fea0a6eb2b271b0/packages/splitcast-rs/src/agent.rs#L675-L700) · [Sample age](https://github.com/tenzyu/splitcast/blob/ca213f8cc9b5009b603528042fea0a6eb2b271b0/packages/splitcast-rs/src/media.rs#L121-L144)

| Choice | Reliability, cost and compatibility |
| --- | --- |
| Keep one synchronous owner and let long operations yield at health deadlines | Resumable OBS waits could run due samples on the same thread while retaining the 3 s bound and the existing client API. Each blocking connection, partial write and scene readback would need a resumable position and a Stop path. Merely raising the bound or re-priming the baseline after a long command would hide a real observation gap. |
| **Move only Running health reads to one owned production thread** | Same upstream queries, same bounds and one mutator. One thread during Running, one latest snapshot, one terminal result. No capture-side work, command-protocol or media change. |
| Subscribe to upstream output-state events and monitor progress counters | OBS events can report transitions promptly. A source can remain Ready and an output active while counters stall. Preserving the media invariant still needs the MediaMTX path snapshot and OBS byte/frame samples. Subscription, reconnect and initial snapshot handling add state alongside that periodic work. [MediaMTX path API](https://github.com/bluenviron/mediamtx/blob/v1.18.2/api/openapi.yaml) · [OBS requests and events](https://github.com/obsproject/obs-websocket/blob/1fcb95b15aa88b1b7e9bda3f9c8650e314377169/docs/generated/protocol.md#getstreamstatus) |

**Frozen change.** Keep synchronous Start readiness and the attempted output in `SessionProfile`. Transfer the accepted ingress/OBS baselines to **one** observer when the effect owner commits Running. Failure to start it fails Start and compensates. Use the original generation/session identity and a fresh, finite operation for each sample. Never carry the Start request ticket or its deadline into a long recording. Sample about once per second, monotonically, one cycle in flight, no catch-up burst. Parse the one bounded MediaMTX document once for all required paths. Preserve exact duplicate/missing/codec rules. Query the owned authenticated OBS using the existing finite connection path. Preserve strict stream byte **and** frame deltas, positive recording byte deltas and `frame_health=unknown` for recordings.

### 3. Carry the processed microphone directly from FFmpeg to OBS

**Invariant.** Only selected microphone samples, processed on production with the configured RNNoise chain, enter the distinct `MicProcessed` OBS input. Game audio, the physical default devices and the speech-return sink are independent. Mute, signed sync offset, clip protection, separate-track routing, silence and failure reporting must survive the replacement.

**Verified structure.** `audio::server` creates a private native socket, cookie, startup script and mono null sink. FFmpeg writes 48 kHz mono PCM to it with a 100 ms buffer request and 1,920-byte prebuffer. OBS captures the matching monitor. Two `pactl` inventories gate startup. This server has one intended writer and one intended reader. Decoding and configured DSP have already happened before the sample enters Pulse. `--disable-shm=yes` and the monitor add a server crossing and scheduling boundary. An exact count of userspace copies needs measurement. [Private audio implementation](../../packages/splitcast-rs/src/audio.rs) · [DSP argv](https://github.com/tenzyu/splitcast/blob/ca213f8cc9b5009b603528042fea0a6eb2b271b0/packages/splitcast-rs/src/media.rs#L296-L334) · [Startup order](https://github.com/tenzyu/splitcast/blob/ca213f8cc9b5009b603528042fea0a6eb2b271b0/packages/splitcast-rs/src/agent.rs#L416-L488) · [OBS routing](https://github.com/tenzyu/splitcast/blob/ca213f8cc9b5009b603528042fea0a6eb2b271b0/packages/splitcast-rs/src/obs.rs#L452-L498)

**Inferred hot-path effects.** One second of 48 kHz mono s16le is 96,000 bytes. A kernel pipe still involves copies, backpressure and wakeups. A full pipe blocks this production writer and can move buffering upstream through RTSP/TCP. OBS also buffers and schedules. Raw PCM removes Pulse's sink clock and contains no capture timestamps. Measure pipe capacity at runtime and cap the prototype at 8,192 bytes (85.4 ms of PCM). Measure startup age and drift across the *whole* chain, including demux probing and OBS buffering. Keep the FFmpeg filter process so a plugin crash remains individually observable. The design adds no direct capture-side work. Shared transport backpressure can still affect capture. Production CPU/RSS, render lag and gameplay effects are **unverified**.

In the offline bounded comparison, FFmpeg directly hashed the configured filter's PCM, then a second FFmpeg demuxed that PCM from stdin. At fixture VAD zero, both digests matched and the output was exactly 96,000 bytes. This supports the transport representation.
